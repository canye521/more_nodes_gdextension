# more_nodes_gdextension

此项目本意是制作更多的Godot节点类用于自用,目前仅完善了GPGPU.

## 模块

- **GPGPU** — Godot支持计算着色器,但是需要自己去创建rd本地渲染设备,GDS侧去管理RID释放,以及当GPU计算完成时,需要堵塞主线程才能读回数据,为了更好的解决这些问题,而构建的GPGPU类.

GPGPU自身管理一个线程,将堵塞主线程变成了堵塞GPGPU自己创建的线程,实现异步的计算,只需要在GDS中去连接特定的信号就能得知计算完成.
通过在主线程中,创建共享纹理Texture2DRD,后台线程去引用主线程创建的纹理,计算完成后结果无需返回CPU可直接在GPU中渲染出来.


ping-pong:
计算着色器不能对同一张纹理原地的进行读写,因此每轮必须读a写b下一轮读b写a,这样两张纹理交替,用户仅需要一条声明pingpong对,即可自动在迭代计算时.反转纹理,让计算能够以pingpong的形式进行.
实现原理：后台线程维护每个 pingpong 对的“写入计数”，每有一个 pass 写这个 pair 就 +1。pass 执行前按计数的奇偶决定这一轮读 a 还是读 b.


多管线:
通过控制一个管线对象,控制一组管线,起初为了能支持多GLSL的同时使用,有跨管线传递RID,不同管线之间只需要传递RID即可实现纹理共用,但是多个GLSL需要多次写重复的绑定,于是引入了管线对象类,在GDS侧只需要操作一个管线对象即可,对于一项计算任务被拆分为多个GLSL,并且GLSL中绑定变化不大且大多绑定都是重名时,可以直接一次绑定,给多个GLSL使用(GDS 侧 set_image("state_input", img) 一次，所有 pass 里叫 state_input 的 binding 都拿到这张图).

引入多个GLSL,本质上会仍然会创建多个管线,每个GLSL都会创建管线,只是方便了管理.

一个管线对象中有多个管线时,称其中的为pass,每个pass都是需要有自己的独立的GLSL的,管线对象可以同时对一堆pass进行流水迭代.
在管线对象之中引入了link,link 让两个 pass 里不同名字的 binding 指向同一张纹理.例如 pass 0 的 state_input 和 pass 3 的 state 实际上是同一张图，link(0, "state_input", 3, "state") 之后，两边解析到同一个 tex_id.


注意 :当使用ping-pong时,务必保证整条pass链上的,ping-pong完整,如pass1上写了一个ping-pong对但是pass2不需要但是pass3需要这个ping-pong对,那就需要pass2透传过来,即便不用也需要写.
原因：flip 计数只在 pass 写 pingpong 时 +1, pass 2 不写会导致计数落后,后续 pass 的 uniform_set 绑错纹理,结果错误但不报错.


实时渲染:
当需要实时渲染的计算任务时,例如实时的水力侵蚀,主线程会不停的向后台线程提交任务,这个时候会产生读写冲突,因为后台线程一直在写入与主渲染设备共享的纹理,所以引入了三缓冲,解决显存被同时读写导致的显示闪烁问题,主线程需要调整投递任务,不能无限制的投递任务,需要等上一个任务完成的信号后再投新的任务.
